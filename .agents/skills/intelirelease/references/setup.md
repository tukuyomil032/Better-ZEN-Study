# Setup interview and configuration

Use this reference to gather the minimum information needed for a repository-specific release setup. Ask about build prerequisites first and updater prerequisites second, before inspecting project files. Ask one question at a time and skip information the user has already provided. After those initial questions, inspect the repository and use its files to avoid asking the user to repeat documented details.

## Start with prerequisites

Ask about build prerequisites first, then updater prerequisites. A useful opening is:

1. **Build:** “Does your current project already build the packages it will distribute, including any signed updater artifacts?”
2. **Updater:** “Is the updater already configured to download updates in the packaged app?”

These are prompts, not a fixed script. If the user has already provided the information, move on to the next question. Once both initial questions are resolved, inspect the repository's source of truth and confirm the finding in the summary.

## Inspect the repository

Before editing, read the files that own each behavior. Prefer project scripts and configuration over assumptions based on a framework or a similarly named project.

- **Version:** Identify the authoritative file and every required mirror. Check how the current app or build reads the version. Do not write versions into files based only on their filenames.
- **Build:** Find the actual commands, required tools, target platforms and architectures, signing/notarization steps, and artifact output paths. Record which artifacts are intended for release and their exact names or naming rules.
- **Updater:** Identify the provider, metadata format, public feed URL, current URL consumers, and the existing updater configuration. Do not inspect or expose secret values.
- **Release workflow:** Read current CI/release workflows, default branch, tag format, branch protections, and repository permissions where available. Distinguish a checked-in rule from a setting that must be verified in GitHub.
- **Release notes:** Locate any existing `CHANGELOG` and release-note generation rules. Preserve existing conventions unless the user chooses a change.
- **Homebrew:** If stable Homebrew distribution is in scope, locate the current tap or cask ownership and update path before proposing a change.

When an item cannot be verified, state what evidence is missing and keep only the dependent part on hold. Do not invent a signed artifact name, feed format, or permission requirement.

## Ask for remaining decisions

Use only the options that fit the repository. Present a short recommendation based on inspected evidence, then ask for one decision at a time.

| Decision | Options to offer |
| --- | --- |
| Setup scope | Local files; prepare a pull request; include GitHub settings. If settings are selected, still agree whether the setup changes should be delivered locally or through a pull request. |
| Workflow trigger | Prepare a release PR and build on its merge (default); build on tag push; build by manual dispatch. Explain whether the selected trigger can publish anything, and ensure setup itself does not trigger it. |
| Release branch | The repository's existing release branch, default branch, or a new named branch if the current flow requires one. Verify the name and branch rules. |
| Release channels | Stable only; stable and beta. Follow existing version/tag conventions. |
| Updater feed destination | GitHub Pages, a raw file URL, or Release attachments, but only when compatible with the updater's existing URL and metadata format. If a raw URL is branch-backed, ask for the branch separately. |
| Feed branch | A dedicated named branch or the default branch, only when the selected feed actually uses a branch. A branch stores files; confirm the public URL the app already fetches. |
| Publication mode | Automatic or draft for manual review. Keep any existing protection or approval requirements. |
| Implementation language | JavaScript, Python, or Bash. This selects the release helper language. The workflow examples use Bash to call it and to connect existing packaging tools and GitHub CLI. Tell the user about this before they choose. |
| Changelog | Keep an existing `CHANGELOG` as-is. Offer integration only when the current setup conflicts and the user chooses it. If no changelog exists, use autogenerated release notes unless the user opts into creating one. |
| Stable Homebrew | None; the same repository; another named tap. Verify the actual destination before preparing changes. |
| Delivery of branch changes | Direct push or pull request. Use the user's selected scope and repository permissions; do not push without explicit authorization. |

If two choices conflict with one another or with inspected repository behavior, explain the conflict and ask only for the affected decision again. Keep independent decisions intact.

## Configuration file

Persist agreed, non-secret decisions in `.github/release-setup.json`. Update only the fields that have been established; preserve unrelated existing settings and unknown fields. Do not fill an unknown value with a plausible default.

The core version-reading contract supports `versionFiles` entries in either form:

```json
{
  "versionFiles": [
    { "path": "package.json", "kind": "json", "key": "version" },
    { "path": "Cargo.toml", "kind": "text", "prefix": "version = \"", "suffix": "\"" }
  ]
}
```

For `kind: "json"`, `key` is a dot-separated path, such as `package.version`. For `kind: "text"`, `prefix` and `suffix` delimit one semantic version match in the file. Paths are relative to the repository root. The current parser accepts `X.Y.Z` and `X.Y.Z-beta.N`; if the repository uses another version scheme, report the incompatibility instead of translating it silently. Each text pattern must match exactly once, and all configured mirrors must agree. Verify the matched value against the authoritative version; never silently choose among conflicting mirrors.

The runtime wrapper is `scripts/intelirelease`; it dispatches to the selected JavaScript, Python, or Bash implementation. Its core commands are `read-version <config-path>` and `prepare <version> <config-path>`. JavaScript and Python use their standard libraries. The Bash implementation requires `jq` and the usual GNU runner utilities. Workflow-specific dependencies and permissions are described in [workflows.md](workflows.md).

An optional changelog input may be represented as `changelog: { "path": "CHANGELOG.md", "notes": "..." }`. Treat `notes` as computed input to `prepare`, not as a secret or as evidence that a release has been published. Preserve the repository's existing changelog file unless the user has chosen an integration or creation change. When the user opts into a new managed changelog, create its heading during setup so the preparation command has a file to update.

For updater configuration, follow the provider-specific contracts rather than inventing fields here. `feed.baseline` records verified Stable/Beta versions only when adopting an existing feed. Tauri uses `feed.tauri.artifacts` for platform-to-artifact basenames and `feed.tauri.paths` for channel paths mapped to targets or `aggregate`. Electron and Sparkle use their provider metadata mappings. For exact layouts and examples, read [feeds.md](feeds.md) and [publishing.md](publishing.md).

If Stable Homebrew is selected, its configuration uses `homebrew.repository`, `branch`, `method`, `slug`, `name`, `description`, `homepage`, and `artifacts`. Confirm the tap and app name from the repository before preparing a Cask; see [publishing.md](publishing.md).

Use the following keys alongside `versionFiles` to keep the generated workflows and the interview in sync. Record only agreed values. Include optional objects when they apply.

```json
{
  "releaseBranch": "main",
  "trigger": "prepare-pr",
  "publishMode": "auto",
  "channelMode": "stable-beta",
  "scriptLanguage": "javascript",
  "changelogPolicy": "preserve",
  "feed": { "kind": "pages", "provider": "tauri", "branch": "gh-pages", "root": "." },
  "setup": { "scope": "local", "delivery": "local" }
}
```

Use `prepare-pr`, `tag`, or `manual` for `trigger`; `auto` or `draft` for `publishMode`; `stable` or `stable-beta` for `channelMode`; and `javascript`, `python`, or `bash` for `scriptLanguage`. Set `changelogPolicy` to `preserve` or `managed`. Feed kinds are `pages`, `branch`, and `release`; provider values are `tauri`, `electron`, and `sparkle`. For setup scope use `local`, `pr`, or `github-settings`; delivery is `local` or `pr`. Keep repository-specific signing requirements and credentials with the existing build. If additional secret references are necessary, store only their names.

## Apply the chosen scope

1. Extract the selected language script, create its launcher, and adapt the build and provider hooks to the repository's verified inputs. Generate the workflow files and remove the unselected build triggers; the resume workflow still supports manual delivery retries. Align the workflow's dispatch guard with the protected branch where it is registered, and its checked-out release ref with the selected release branch. Keep the actual release and feed URLs compatible with the installed app.
2. Validate the generated YAML, smoke-test the release helper and provider producer with fixture data, and inspect the resulting diff. Keep existing site and workflow files that another process owns unless the user selected a compatible integration.
3. For PR scope, deliver the checked changes through a review branch and PR. Inspect the trigger first so creating the setup branch or PR cannot start a release. Leave the release branch, tags, and live feed to the existing release process.
4. For GitHub settings scope, inspect current settings and propose only what the chosen setup requires. Typical changes are creating the confirmed feed branch, selecting GitHub Actions as the Pages publishing source, or enabling Actions to create PRs. Preserve existing protections, and report settings blocked by organization policy or unavailable permissions. Use an authorized GitHub tool or CLI to apply the previewed changes; read them back and report the observed result. If a feed-branch creation would start an existing deployment, leave that step to the user or agree a compatible rollout before applying it.

## Before handing off

- Summarize verified repository facts separately from user decisions.
- Name the exact files prepared and list the remaining unknowns.
- Confirm that setup did not run a release, publish files, push a tag, or modify application/updater secrets.
- If GitHub branch settings are involved, present the preview and report whether it was applied or only prepared.
